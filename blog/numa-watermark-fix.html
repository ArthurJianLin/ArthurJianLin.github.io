一次「读操作」清零了回收阈值：NUMA 水位 bug 的定位与修复

2026-10-05 · 约 8 分钟 · #mm #numa #sysctl
对应补丁：874611d193f2 @ torvalds/linux

0x00一个反直觉的现象

最隐蔽的 bug 往往不是"某个操作坏了"，而是某个什么都不该发生的操作，悄悄改了状态。

这个问题的现象出现在多核 NUMA 服务器上：内存回收行为出现抖动——回收阈值忽然失真， kswapd 与 direct reclaim 的触发像是被人随机干预过。而排查的结果是：触发条件仅仅是 读取了一个内存相关的 sysctl 参数。

没有写入，没有配置变更，cat 一下，节点的回收阈值就归零了。

0x01背景：per-node 的回收阈值在哪

除了大家熟悉的每个 zone 的 min/low/high watermark，内核在 NUMA 节点级别还维护着一组 回收决策参数——用于判断"这个节点上还有多少比例的页面值得回收、 什么条件下继续持有"。这组参数挂在每个节点的 struct pglist_data（pgdat） 上， 通过 sysctl 暴露给管理员调节。

这类参数有个共同特征：它们是每个 node 一份。所以 sysctl handler 要更新它们时，必然要遍历所有 online node 逐个赋值。问题，恰恰就出在这个"逐个赋值"的循环里—— 它被读写两条路径共享了。

0x02根因：读路径复用了写路径的副作用

sysctl handler 的经典反模式长这样：handler 定义了一个局部变量承接参数值，检查、处理， 最后不管这次调用来自内核还是用户、是读还是写，都会把值回写到全局状态。

在这个 bug 里，读路径上那个局部变量并不是管理员设置的值——它要么是默认值，要么根本没有经过 有意义的初始化。但 handler 照样走进了"遍历每个 node、更新 min ratio"的赋值循环。 结果就是：一次纯读操作，把每个 NUMA 节点的回收阈值改写了一遍。 

/* 反模式示意，非原 diff */
static int handler(...) {
        int val = ...; // 读路径上：不是用户写入的值

        // 这段逻辑本应只属于写路径：
        for_each_online_node(nid) {
                NODE_DATA(nid)->min_ratio = val; // 读一下 = 全节点改写
        }
        ...
}

阈值被清零后，节点级的回收决策就失去了正确的参考点：本来不该回收的时候开始回收， 该回收的时候判断又可能失准，宏观上就表现为多核 NUMA 服务器的内存回收抖动。 这种抖动在单次监控里很难直接归因——毕竟谁会怀疑一个 cat 呢？

0x03定位思路

  • 把"谁在改状态"和"谁在读状态"分开：回收阈值属于内核内部状态，先确认管理员侧没有并发写入（audit / shell history）。
  • 最小化复现：在一台干净的 NUMA 机器上，读操作前后分别抓取节点参数与水位，确认"读"本身改变了状态。
  • 锁定 handler：顺着该 sysctl 的注册点找到 handler，检查局部变量的生命周期与赋值循环的可达性——读路径也会走到它。

0x04修复：让写回到写的地方去

修法说起来只有一句话：仅写操作更新 NUMA min ratio。

读路径只负责把状态带出去，不再触碰任何全局状态；写路径在校验通过后再执行遍历赋值。 这和我在另一个补丁里处理的 lowmem_reserve_ratio 是同一个哲学—— 读路径必须无副作用，代价再小的副作用乘上读取频率都是灾难，更别说清零阈值。

0x05影响与收尾

修复已合入 Linux 主线（torvalds tree），会随主线发布进入所有发行版。对所有多节点的服务器 ——从两路的整机到大规模 NUMA 的机架机器——读一个 sysctl 不再是他们负载曲线里的一颗暗雷。
