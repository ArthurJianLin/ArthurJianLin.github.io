把探针开销压进 2%：eBPF 可观测性平台的设计取舍

2026-10-09 · 约 11 分钟 · #ebpf #observability #performance
技术栈：eBPF (libbpf/BCC) · LKM · C/C++ · gRPC · Protobuf · MySQL

0x00"低开销"是约束，不是口号

做内核可观测性平台的第一个决定不是"采什么"，而是给自己立一条红线： 探针整体运行开销不得超过 2%。因为可观测性工具的第一要务是不改变被观测系统—— 探针一旦成为生产负载的一部分，你采集到的所有数据都开始自带偏差， 长尾延迟越量越量的本质就变成了"探针打点抖动"。

这套平台服务于大规模服务器集群上的云电脑业务，要解决的是微服务场景的长尾延迟 与内核态异常难以排查的问题。无侵入（不改业务、不打补丁进生产内核）是第二条红线。 所有取舍都从这两条红线推导出来。

0x01工具面：七个方向的内核追踪

  • 调度延迟统计——runqueue 里等了多久、谁在加塞；
  • 进程生命周期追踪——exec/exit 全程回放；
  • VFS 文件操作监控——慢路径落到哪个 inode；
  • Slab 内存统计——哪个 cache 在涨；
  • 慢 IO 分析——从块层视角拆解延迟；
  • Off-CPU 阻塞分析——CPU 不忙但请求慢的那部分时间去了哪；
  • KVM 虚拟化卡顿观测——对应云电脑场景的"画面卡一下"。

工具集的设计原则是按事件源切，不按指标切：每个探针围绕一个内核事件源 （tracepoint / kprobe）组织，跨工具复用同一套采集与上报通道。eBPF 用于绝大多数场景， BPF 覆盖不了的深水区用 LKM 补位（这也是为什么平台是"eBPF + 内核模块"双引擎）。

0x02关键取舍一：直方图放进 BPF Map 里算

P90 / P99 尾部延迟是怎么来的？不成熟的实现是：每个事件把时间戳带出来， 用户态聚合算分位数。这在高频事件（比如每次调度）下等于把采样风暴倒给用户态， CPU 和内存双爆炸。

我们的做法是把延迟直方图直接建在 BPF Map 里：内核态按 bucket 累加计数，用户态只以低频周期读取直方图快照再算分位数。数据在源头就被压缩了几个数量级， 用户态拿到的永远是聚合结果而不是原始事件流。这也是我们建立云电脑卡顿基线的数据来源。

0x03关键取舍二：聚合必须在内核态完成

网络监控是同样的道理。收发包路径是内核里最热的路径之一，在这里埋点， 第一原则是：每个包的事件处理时间必须接近常数，且绝不共享可写状态。

所以网络 eBPF 埋点用的是 PERCPU_ARRAY map——每个 CPU 一份独立计数器， 内核态完成收发包指标聚合，没有跨核争用、没有锁、没有 cacheline 弹跳。 用户态合计 per-CPU 计数即可得到高精度网络指标。这条"内核态聚合"纪律， 是探针开销能压在 2% 以内的最大功臣。

0x04验证：怎么证明自己没骗自己

低开销必须被测出来，而不是设计出来。我们的验证分两层：

  • 开销层：用 stress-ng 构造 CPU 抢占、iperf3 打满网络、工具脚本制造 IO 瓶颈——在探针全开与关闭两种状态下跑相同的压力负载， 用 perf 对比吞吐与 CPU 占用差异，这就是那个 "2%" 的出处；
  • 准确性层：指标不能只是"有"，还得"对"。以已知正确的统计 （/proc 数据、perf 计数）为参照，校验直方图与聚合指标的准确度， 尤其是负载高峰下的一致性。

这一步最容易被省掉，但它恰恰是平台可信度的地基：没有对照组的监控数据， 只是比较好看的数字。

0x05数据通道与落库

采集端与后端之间走 gRPC + Protobuf：二进制序列化紧凑、跨语言，agent 端 C/C++ 实现不用背重型依赖；指标落 MySQL，按维度建索引支撑长期的基线对比。 这个选型不性感，但它足够无聊、足够稳——对生产系统来说， 无聊是优点不是缺点。

0x06小结

  • 先立红线（无侵入、<2%），所有设计从红线推导；
  • 高热路径的答案是 PERCPU 内核态聚合，直方图进 map；
  • 指标的准确性要和开销一样认真地被验证——用压力工具和 perf 做对照；
  • 数据通道选成熟无聊的技术，把风险预算省给内核侧。
